Declarative Architecture Notes

Standalone documentation capturing the architectural discussion on KeshavSoft's JSON-first, instruction-driven construction system alongside a static source review of the 25-1.zip snapshot.

The base is not the code. The base is the meaning.

This site indexes and summarizes the notes without overwriting source facts or resolving open design questions prematurely. Every claim distinguishes discussion principles from static ZIP inspection.

01 · Foundation & Core Principles

01-executive-overview.md 02-core-principles.md

Information and variable requirements are expressed as JSON. A stable semantic base is prepared first, and ordered instructions apply transformations or mutations to produce a presentation structure (table, list, select, datalist, or form).

7 Conceptual Layers

  1. Information / data — records and values.
  2. JSON representation — nodes, properties, children.
  3. Base — stable semantic skeleton (not code).
  4. Changes / options — collections, files, columns, tags, features.
  5. Instructions — ordered declarative steps.
  6. Transformations / actions — reusable value or tree mutators.
  7. Output / presentation — structure rendered to browser DOM.

6 Core Principles

  1. JSON-first, not HTML-first — HTML is one presentation output.
  2. Stable base + variable changes — externalize changing inputs.
  3. Declarative steps — specify what, where, and which template/action.
  4. Mutation after skeleton — build once, then mutate existing regions.
  5. Construction ≠ mutation — generators vs in-place template writers.
  6. Table is an example — data lists, selects, and forms share the model.

02 · JSON-First Model & Base Separation

01-json-first-model.md 02-base-changes-construction.md

Inspired by the HTML DOM tree, components are represented as JSON objects with properties and child nodes (table, thead, tbody, tr, th, td): 

information → JSON representation → construction/transformation → presentation
Conceptual separation of construction concerns
Concern Question it answers
Base What stable semantic structure exists?
Input / change data What varies for this particular use?
Instruction What ordered work should happen?
Selection Where in the existing JSON tree should it happen?
Template / transform What value or structure should be created?
Mutation action How should the destination be changed?

03 · Two Row/Column Construction Strategies

01-row-column-strategies.md

Header and body use separate construction logic. In declarative-instructions/src/v2/instructions.json, buildHeader and buildFooter are single instructions using fromCollection over $.columns, while body/select/datalist use two-dimensional strategies:

Strategy A — rowOnColumn

Iterate records, create each tr, populate its cells across columns, and append to tbody.

Verified in ZIP: used by buildBody with buildBodyTr and buildBodyCell.

Strategy B — columnOnRow

Establish rows first, then iterate columns to insert cells into existing rows in a second phase.

Verified in ZIP: used by buildSelectWithOptions and buildDataListWithOptions.

Status: No universal winner has been selected pending comparative evaluation of ordering, mapping, and performance.

04 · Instruction Execution Lifecycle

01-instruction-lifecycle.md

Verified in json-renderers-run-instructions/src/v20/index.js and src/v20/instructions/index.js:

  1. Look up definitions[instructionMainKey]?.[instructionSubKey].
  2. Obtain spec[definition.baseFromSpec] and clone it with structuredClone.
  3. Normalize modern grouped options and legacy show* aliases (showSearch, showSerial, showOptions) into ordered, deduplicated instruction keys.
  4. Create shared mutable state { base, data } and execute steps in order.
  5. Dispatch arrays via executeWriteBundle (checking skipIf, cloning templates, calling writePath) and objects via executeBuildInstruction (single, rowOnColumn, columnOnRow).
  6. Return the mutated state.base for conversion via @keshavsoft/json-to-dom in table renderer V58.

07 · Design Options

01-rebuild-vs-incremental-update.md 02-json-validity-and-contract.md

Rebuild vs. Incremental Update

Option A (Rebuild from base): Clone clean base, rerun instructions with latest data/options, replace output. Deterministic and simpler baseline.

Option B (Incremental mutation): Diff old/new records, target affected nodes, preserve UI state—requires stable record identity and reconciliation semantics.

Four Levels of “Valid JSON”

  1. Syntactic: parseable JSON syntax.
  2. Structural: expected node shape, properties, children.
  3. Semantic: recognized component regions (e.g., table-body).
  4. Executable: referenced definitions, instructions, templates, and paths resolve cleanly.

08 · Open Questions (26 Unresolved Topics)

01-open-questions.md

Next recommended discussion: formalizing the JSON node contract and the boundary between semantic base and presentation spec.

Expand all 26 open questions across categories A–F

A. JSON model and meaning

  1. What exact JSON shape is considered a valid node in the platform?
  2. Which properties are universal node properties, and which are element-specific?
  3. Is the JSON model intended to represent only DOM-like output nodes, or broader application meaning as well?
  4. What is the boundary between semantic base and presentation-specific spec?

B. Base and external changes

  1. Which parts of a component must always exist in the base?
  2. Which features must always be external data/options?
  3. Can a base be shared by multiple presentation renderers?
  4. Is the base immutable after cloning, or is mutation the intended normal execution model?

C. Construction strategies

  1. What are the exact semantics of rowOnColumn and columnOnRow in the two-dimensional package?
  2. Which strategy is best for table body construction, and under what conditions?
  3. How should header, body, and footer construction differ?
  4. Can a single column-oriented instruction consistently handle header, body, and footer, or should these remain distinct steps?

D. Instruction and mutation model

  1. What is the formal contract for an instruction: type, sourcePath, destinationPath, templateKey, func, action, skipIf, narration?
  2. Should instructions be declarative only, or may an action contain specialized imperative behavior?
  3. How are ordering dependencies represented and validated?
  4. Should every destination JSONPath resolve to exactly one node, or should some instruction types explicitly support many matches?
  5. Should row-aware actions remain custom write-path actions, or become first-class instruction types?

E. Runtime lifecycle

  1. When data changes, should the system rebuild from the original base or incrementally reconcile the existing tree?
  2. How should stable row identity be represented?
  3. How should sorting, filtering, pagination, and row insertion interact with serial numbers?
  4. How should mutations preserve UI state and event bindings when DOM is re-rendered?

F. Compatibility and package lifecycle

  1. Can all active dataRole destinations be migrated to JSONPath?
  2. Is findByRole still required for any supported consumer?
  3. Which focused transformation packages are current public contracts?
  4. What is the compatibility matrix among definitions, instructions, spec, runner, write-path, and renderer versions?
  5. Which historical versions are supported, and which are archival only?
